# 有来源的长期记忆

## 存储与迁移

管理端会话存储使用 `companion/memory.sqlite`，当前 schema 版本为 2，SQLite WAL 与 FULL 同步提交。程序首次启动将旧 `memory.json` 导入私有临时数据库，逐会话核对兼容快照、状态与原文哈希后在同一卷原子发布；原 JSON 和 gzip 归档保留。失败不会用空库覆盖旧记录。SQLite 文件、WAL 和 SHM 属于用户数据，备份应使用在线快照或停止 Web 后整体备份。未知或导入未完成的数据库在只读预检阶段被拒绝，不执行 DDL 覆盖。

原始事件独立于活跃上下文保存。新用户原话完整保存，媒体观察另表保存；活跃聊天仍有兼容预览。旧 JSON/归档只有旧版保留下来的内容，完整性标记为未知，不能恢复此前已截断的正文。相同正文但不同消息身份不会合并；媒体记录同时区分原请求与实际素材键。

写入只复制、提交涉及的会话与全局计数，不再为每次发言序列化所有会话。收到新消息、发送声称、实际接受、设备观察和素材状态仍使用原业务入口；记忆文本不能改变任务或回执。

## 提取与召回

默认记忆维护在同一会话新增 12 条用户消息或空闲 300 秒后批量处理，实例内模型维护调用串行执行。来源按 UTF-8 分块，长原文的尾部不会因为提取输入预算被删除；提交进度按完成的原事件推进，失败/重启按幂等候选继续。模型输出必须具有真实事件编号、同一作用域内的真实发送者和精确原文引句。模型推测标为待核实；明确更正建立版本关系，同义事实可合并来源。

四种条目用途为事实、偏好、事件与经验；连续性快照是有来源的固定事件，保留当前话题与未完约定，不能修改人格与权限。普通事件 72 小时内优先细节，之后优先短摘要，14 天后为冷候选；助手复述、维护与检索不会刷新用户有效提及时间。冷检索不惩罚事件年龄。

词法索引使用中文字符/二元组与归一化英文词项。配置嵌入服务后，词法排名与向量排名通过倒数排名融合；向量绑定服务、模型版本、维度和条目版本。未配置或调用失败会明确回退到词法检索，不能宣称真实语义召回已验收。配置由 `/api/memory/services` 私有保存，返回视图不含密钥；更换服务主机须提供新密钥。嵌入调用只处理查询和有来源条目，不上传整库聊天。

`memory_search/read/remember/update` 按需发现。普通成员只读当前会话，写入/更正归属本人；跨会话查询仍需真实管理员身份、跨会话授权与本账号已知目录。分页返回版本绑定游标，变更要求重新查询。当前会话的自动召回不自动读取其他会话。跨会话资料是本次获准任务的来源，不成为当前群的共同经历。

清除会话建立持久屏障，已有原始事件、派生记忆和向量都退出自动读取；不会从旧归档重新建立它们。单条遗忘同时屏蔽其原始来源，相关条目不会通过换一种表述重新进入上下文。只读历史归档保持原有管理端阅读语义。

## 上下文与费用

自动注入初值：近期对话 4096 Token，长期记忆 4096 Token，其中固定与连续性额度 1024 Token。均可配置，不限制显式分页读取。没有对应 tokenizer 时使用标记为估算的文本计数；真实账单以提供商报告的用量为准。配置模型窗口后，必要请求或工具协议超出窗口会返回具体原因，当前请求不被悄悄截断。

新记忆模式关闭自动反复压缩旧滚动摘要；旧摘要与笔记保留为兼容资料，显式管理操作仍可执行旧压缩。固定人格、权限与工具协议前置，动态状态和来源条目后置。工具循环压缩前重新核对条目版本、遗忘屏障与原始来源，当前请求、有效补充和工具结果配对不通过正文截断来腾出空间。上下文计量只存数值组成与计数方法，不保存提示正文。

模型用量按 conversation、compression、memory_extraction 区分目的，维护与嵌入另有带日期、报告/估算标记的记忆用量。自动维护默认每日 100000 Token，0 表示不设日预算；达到预算保留进度。手动重建明确不受自动日预算限制，运行任务纳入 Web 排空和退出等待。

## 维护命令

使用 `go run ./cmd/wechat-memory --dir <companion目录> --action inspect` 只读检查，不输出正文、不初始化数据库。`dry-run` 在私有临时副本预演并校验，不启用数据库；`verify` 检查 SQLite 完整性；`migrate` 执行兼容导入；`backup --out <新文件>` 创建一致在线快照；`index --scope <作用域编号> --batches 20` 分批补建旧归档索引并保存续建位置。`index --all-scopes --batches 20` 每作用域处理指定批次数，返回聚合完成状态，未完成可重复执行。显式迁移时停止 Web 服务，保留原生微信服务。

管理端会话提供长期记忆、来源、版本、更正、固定和遗忘入口；系统提供维护/嵌入配置与整理进度。长正文沿用预览加大弹窗。

## 依赖与验证边界

SQLite 驱动固定为 `modernc.org/sqlite v1.38.2`，使用主程序的 Go 工具链，无 CGO。驱动 BSD-3-Clause 许可证和传递依赖各自许可证随 Go 模块版本固定；SQLite 本体为公有领域。无需独立数据库服务或本地嵌入模型运行时。

合成回归、来源 Top-5、性能、Token 估算与隔离真实模型证据见 [验收记录](memory-acceptance.md)。嵌入适配器通过不代表未配置的真实语义服务已经验收。

## 本机更新与恢复

1. 验证源码、推送并确认对应 SHA 的 CI；构建 Windows/Linux 可执行文件，运行 SQLite 备份测试。
2. 在现有 Linux 部署所有者身份运行 `python3 scripts/update_local_memory.py --expected-sha <已验证SHA>`。默认无限等待在途任务自然结束，不取消任务。脚本只停止 Web，原生微信持续运行。
3. 排空后建立持久暂停标记，在私有部署根 `backups/memory-upgrade-<时间>/` 保存旧程序与控制数据快照；SQLite 使用在线备份，媒体和模型留在原处。逐库检查、预演、迁移、索引全部归档并再次校验，再替换 Web。
4. 新程序在暂停状态提供只读管理接口。脚本核对健康、原生登录、配置/素材索引/收件队列哈希与有鉴权的原始来源读取，最后调用需要登录及 CSRF 的 `/api/runtime/memory-activate` 才恢复新处理。结果摘要写入私有备份的 `result.json`；不输出会话正文或凭证。

激活前出错：脚本停止新 Web，保留失败 SQLite 到备份诊断目录，恢复旧可执行文件和迁移前数据库（原 JSON 始终保留），解除暂停并启动旧 Web。备份未完成时尚未迁移，不替换数据。需要手动恢复时，应先停止 Web，核对备份所属 SHA 与时间，再依照同一顺序恢复，不能直接覆盖运行中的数据库。

激活请求发出后，即使 HTTP 结果不明确，也禁止自动回切旧 JSON。此时暂停新处理，保留 SQLite 与 WAL，通过兼容 schema 的版本修复；旧 JSON 已不能代表新写入。原生登录、媒体原件、模型和各自权威任务/回执存储不随程序回滚删除。
